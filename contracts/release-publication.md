# Application release publication contract (v2)

This is the CI contract for application installers published from `YaomuStudio/YaomuStudio`. It replaces the Windows-only draft/evidence/approval gate. It is not a model ReleaseManifest, signing-key provisioner, or authorization to publish. Tag creation and public release remain separate owner actions.

## Release identity

- Accept only existing `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-beta.N` tags with canonical nonnegative integers (no leading zero except `0`). Reject whitespace, shell metacharacters, and non-canonical numbers.
- Resolve the tag to its full 40-hex commit. Root, `ui/package.json`, and `desktop/package.json` versions at that commit must all equal the tag version (with `v` removed).
- Checkout every build and publish job at that exact commit. Do not build from a branch head.
- Stable tags publish as normal releases; `-beta.N` tags publish as GitHub prereleases.

## Trigger and publication

- Automatic builds run only on `push` of a `v*` tag.
- `workflow_dispatch` is a manual rerun/repair path and requires an existing tag; it does not accept branches.
- A tag push builds all platforms. Only after every build succeeds does the publish job create the GitHub Release. A failed build publishes nothing.
- The release is public by default. There is no draft/approval step in this contract.
- If a release with the same tag already exists, the publish job fails closed. It must not delete, overwrite, or `--clobber` it. Recovering a partially uploaded release is a manual owner action.

## Build matrix

| Job | Runner | Target |
|---|---|---|
| `build-windows` | `windows-latest` | NSIS, x64 |
| `build-macos` | `macos-15` (arm64) | DMG + zip, arm64 and x64 in one electron-builder invocation |
| `build-linux` | `ubuntu-24.04` | AppImage, x64 |

- Build jobs use `--publish never`. Only the publish job uploads assets.
- macOS builds both architectures in one invocation so `latest-mac.yml` contains both architectures. Building each architecture separately and uploading two manifests is not allowed.
- `extraResources` selects `desktop/build/core-${arch}` so Core, Python, and FFmpeg match the target architecture.

## Assets

Exact expected asset set for version `V`:

```text
YaoMuStudio-V-win-x64.exe
YaoMuStudio-V-win-x64.exe.blockmap
latest.yml

YaoMuStudio-V-mac-arm64.dmg
YaoMuStudio-V-mac-arm64.dmg.blockmap
YaoMuStudio-V-mac-arm64.zip
YaoMuStudio-V-mac-arm64.zip.blockmap
YaoMuStudio-V-mac-x64.dmg
YaoMuStudio-V-mac-x64.dmg.blockmap
YaoMuStudio-V-mac-x64.zip
YaoMuStudio-V-mac-x64.zip.blockmap
latest-mac.yml

YaoMuStudio-V-linux-x64.AppImage
YaoMuStudio-V-linux-x64.AppImage.blockmap   # optional if electron-builder emits it
latest-linux.yml
```

- No extra executables, checksum files, source archives, or third-party notices are uploaded as separate assets. License/source notices remain inside the installers.
- `artifactName` is configured in `desktop/electron-builder.yml`; local names and remote names must match.
- `latest*.yml` is generated by electron-builder. Do not hand-edit or invent manifests.

## Verification before publication

The publish job downloads all build artifacts into one directory and runs `scripts/verify-release-assets.mjs`:

1. Reject unknown or non-regular files.
2. Require every expected asset.
3. Parse `latest.yml`, `latest-mac.yml`, and `latest-linux.yml` with the trusted YAML parser.
4. For every `files[]` entry: require a safe basename, positive size, nonempty SHA-512, an existing local file, matching size, and matching base64 SHA-512.
5. Require the Windows installer in `latest.yml`, both macOS architectures in `latest-mac.yml`, and the Linux AppImage in `latest-linux.yml`.
6. Require `latest-mac.yml` to contain both `mac-arm64` and `mac-x64` entries.

The build jobs also verify the generated `app-update.yml` points to `YaomuStudio/YaomuStudio` and that the packaged Core/Runner/Python/FFmpeg files exist.

Artifacts are consumed from the same workflow run's artifact store. This contract does not add a separate signed provenance channel beyond the workflow run identity and the asset hashes.

## Signing and platform policy

- Windows builds may be unsigned. Unsigned installers can be distributed, but SmartScreen may warn. The release notes must say so.
- macOS builds are unsigned previews. Gatekeeper requires right-click → Open; auto-update is unavailable. The release notes must say so.
- Linux AppImage builds are unsigned previews. Auto-update is not verified on a real desktop.
- Model execution is Windows + WSL2 by default. Linux host execution is best-effort. macOS model execution is not part of this release. Release notes must state this.
- Do not claim a signature, notarization, or auto-update capability that the build did not produce.

## Release notes

Use `gh release create --generate-notes` plus a short prepended note:

```text
> 未签名构建：Windows 可能触发 SmartScreen；macOS 需右键打开，自动更新不可用。
> macOS/Linux 为 preview；模型执行以 Windows + WSL2 为基线，Linux 为 best-effort。
```

Beta tags must also pass `--prerelease`.

## Permissions and secrets

- Build jobs: `contents: read`.
- Publish job: `contents: write`, using `secrets.GITHUB_TOKEN` only.
- Windows signing, if configured, reads `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` from secrets. Missing secrets produce an unsigned build; they do not block the pipeline.
- No long-lived PAT, no cross-repository token, and no credentials in client binaries or release assets.
- Logs must not print tokens, full environment variables, or private key material.

## Failure and race semantics

- A failed build prevents release creation.
- A failed verification prevents release creation.
- Release creation and asset upload are separate GitHub API calls; this contract does not claim atomic publication. If creation succeeds and upload fails, the release may be visible with incomplete assets. The job must fail and the owner must fix it manually; a rerun refuses to touch the existing release.
- GitHub users or other systems can mutate a release after publication. This contract does not claim an atomic compare-and-swap over the release.

## Relationship to app updates

- `desktop/electron-builder.yml` points `electron-updater` at the public GitHub Releases feed (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`).
- Windows NSIS is the primary auto-update path. macOS unsigned previews do not support auto-update. Linux AppImage update behavior is unverified.
- The app never embeds GitHub credentials; the public release feed is anonymous.

## Retired mechanism

The previous Windows-only `resolve/build/stage/verify/publish` draft gate, `release-build-evidence.json`, `RELEASE_APPROVED_*` repository variables, and Authenticode evidence channel are retired by this contract. They must not be reintroduced into the tag pipeline without a new contract revision.

## Verification boundary

Static workflow tests, asset verification on locally built macOS artifacts, and unit tests do not prove a real Windows/Linux CI run, a real GitHub Release, or a real `electron-updater` upgrade. Those remain unverified until executed on the public repository.
